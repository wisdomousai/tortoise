# Parts desk 4: live model and voice

This chapter continues Parts Desk from [chapter 3](parts-desk-3-context-and-scenarios.mdx). It describes an optional run with a local model and adds dictation to the application's message composer. The dictation step can use the deterministic stand-in without supplying a weight file.

Use the exported repository whose stand-in runs and UI-session tests passed at the preceding checkpoint. The live route requires an explicitly selected GGUF file and a compatible `llama-server` executable. Obtain those files yourself and use the license that applies to the weights. The dictation step can be implemented and tested while the application still uses its stand-in.

No new live-model or microphone result is established by this documentation revision. The recorded conversation below is dated evidence from an earlier run.

## Setup

To continue without live weights, follow [Voice input](#voice-input) manually from the completed chapter 3 application. The tutorial runner executes the live prompt first and cannot record an optional skip.

Run the normal application checks from the export root:

```sh
bun run format
bun run generate
bun run typecheck
bun test showcase/examples/parts-desk
```

The default test suite skips the real-model cases unless their weight file and executable are configured. Inspect the skipped cases in the output; a successful deterministic suite does not report a real model's result.

A dictation screen change also requires:

```sh
bun run build
bunx playwright test showcase/examples/parts-desk
```

## Live run

The development launcher reads `LOCAL_MODEL_GGUF`, measures that file, and writes the model configuration consumed through `PARTS_DESK_MODEL`. It binds the `llm` process to the supplied executable and the local inference destination in its temporary policy. Set `LOCAL_MODEL_LICENSE` to the actual weights' license; the launcher's default value does not establish a file's license.

The model-server plugin verifies the files against the selected entry when starting the process. Inspect the model entry and measured digest in the resulting run. Verification identifies the loaded file. Model correctness must be assessed from its actual tool calls and saved application outcomes.

Use [serve-a-local-model](../../plugins/model-server/skills/serve-a-local-model/SKILL.md) for the implementation and its required checks. Start development from the export root after replacing the paths below:

```sh
LOCAL_MODEL_GGUF=/absolute/path/to/model.gguf \
LLAMA_SERVER=/absolute/path/to/llama-server \
LOCAL_MODEL_LICENSE=the-weights-license \
bun run --cwd showcase/examples/parts-desk dev:web
```

The reference development launch uses port `4389`. Its policy gives local inference a 300-second request timeout, and the assistant definition bounds the run's wall time. Long inference can still exhaust that budget. If a deployment policy is already configured in the environment, inspect its destination and process binding because the launcher keeps that policy.

```text prompt
Use the serve-a-local-model skill. Start showcase/examples/parts-desk with bun run dev:web and
LOCAL_MODEL_GGUF set to the GGUF weights of an instruction model that calls tools. Through
Playwright, hold this conversation in the assistant panel, each message after the previous run
ends:

On the Inquiries screen, start with: "A caller from Northgrid reads TR-404 off the plate. Which
   transformer is it?" Answer its question with TR-40471.
Continue with "Which HV bushings fit it, and are they in stock?"
Then send "Prepare a quote for two of them."
Create the draft in the builder, then send: "They want 15 percent off because of a late delivery."
Finish with "Cancel that quote, the utility found spares in its own store."

Report for each turn the calls with their outcomes, the questions, the approval requests, the
text and the time it took, and say where the model went wrong. Save a screenshot of the panel
after each turn. Add opt-in checks for the ambiguity request and discount approval through the run route when
LOCAL_MODEL_GGUF is set and judges the command results. Run the checks the
serve-a-local-model skill names and report what passed. Do not change prompts or code to make the
model succeed; record what it did in the README.
```

Keep the request sequence in one panel conversation. The ambiguity request concerns `TR-404`; answer its host question with `TR-40471` when it asks. Continue by asking for compatible HV bushings and a prepared quote. Inspect the builder before creating the draft. After creation, copy its saved number so the discount and cancellation requests can be checked against the actual quote.

For every message, inspect the completed run through the host and query the relevant application records. Record the run ID with its model digest. A response that says it prepared a quote must correspond to a form intent in the captured UI session. A discount request must name the saved quote ID and contain a complete input. Approving that request as the supervisor must execute the intended command before the request can be treated as successful.

The reference's opt-in `test/assistant-live.test.ts` contains an ambiguity check and a discount-approval check. The latter creates a known draft fixture, checks that the assistant did not directly change it, and attempts supervisor approval. It reports malformed revision resources and approval failures. It does not run the entire browser conversation.

To execute those cases with your configured files, run from the export root:

```sh
LOCAL_MODEL_GGUF=/absolute/path/to/model.gguf \
LLAMA_SERVER=/absolute/path/to/llama-server \
LOCAL_MODEL_LICENSE=the-weights-license \
bun test showcase/examples/parts-desk
```

Record failures as observed. Changing the prompt or fixture creates a different run and should be recorded with that change. Keep evidence of the initial attempt when repairing an application defect.

## Voice input

Dictation writes into the message composer. The person can edit the resulting text before sending it through the existing run route. This application does not add a model capability for recording audio.

The reference checks whether the browser recognizer exposes `available()` and supports `processLocally`. It requests English recognition with `processLocally: true`. A missing API or an unavailable local recognizer hides the button. A supported downloadable language pack can be installed through the browser before dictation begins. The application has no configured remote speech-service fallback.

```text prompt
Use the build-screens skill. In showcase/examples/parts-desk, add a microphone button to the
assistant composer. It uses the browser's speech recognition only with on-device processing, so
no audio leaves the machine, and it hides when the browser offers no on-device recognition for
English. While it listens, the button shows a pulsing ring in the primary color and the interim
words appear in the text area; the person edits and sends them. Extend the Playwright spec: the
button hides when the browser lacks on-device recognition, and with a stubbed recognizer the
dictated words fill the text area and the composer sends nothing. Say in the README where
dictation ran against a real microphone. Run the checks the build-screens skill names and
report what passed.
```

The finished-reference capability check is:

<Code code={region(dictation, 'recognizer')} lang="tsx" title="Finished reference: ui/assistant-dictation.tsx" />

`useDictation` retains the text present when listening starts and appends the recognizer's current transcript. It sets `processLocally` on the recognition session as well as on the availability request. Typing into the composer while listening calls `abort()` on that session. The browser fixture checks that the person's edit remains in the composer. The composer still requires the normal send action.

The browser test installs the recognizer stub from `e2e/recognizer.ts`. It checks the requested language and the local-processing flag. With recognition unavailable, the button should be absent. With a supported stub, dictated words should appear in **Message** while the host's run list remains unchanged. The test then edits the text and verifies that dictation was aborted.

Run the assistant browser specification after the build. Inspect its dictation case and confirm that it asserts no run was submitted. During the earlier documentation run, headless Chromium crashed when calling the real `SpeechRecognition.available()` method; the fixtures therefore report recognition as unavailable unless the test installs its stub. Those fixtures establish UI handling of recognizer events. They do not establish speech accuracy or successful use of a physical microphone.

For a microphone check, record the browser and operating system with the installed language pack. Verify that a permission refusal is displayed without sending a run, then test that recognized text remains editable. State whether that check was performed. Leave the existing microphone limitation open if only the stub ran.

## Verification record

Keep the deterministic fixture results with the exported application's checks. Record any real-model run separately with its selected weight digest and the observed application outcomes. Preserve the dated failures above until a later run provides evidence about them.

The panel's conversation ID is stored in memory, so a browser reload begins a new conversation. A run retains its last 256 events. Inspect longer runs with that retention limit in mind; absence from the retained event list does not establish that an earlier event never occurred.
