# @agent-native/shell

OS handlers and OS actions at runtime. It checks the syntax of a raw OS request, matches it to the first declared handler that accepts it, fills the handler's target templates, and builds the instruction a shell adapter runs for a declared action. It also generates the platform registrations (Expo, electron-builder, the web manifest) from the same declarations, and holds the desktop and mobile shell adapters without their Electron or Expo calls. The [OS plugin](../../plugins/os/README.md) composes these functions into the shell port; the [desktop starter](../../apps/desktop/README.md) supplies the Electron calls to the adapter.

Layer: framework (`packages/*`). Pure functions with no Node, Bun or browser API, so the host, the mobile host and a browser adapter can share them.

## Trust boundary

A raw request comes from an unauthenticated sender on the device. `parseRawOsRequest` refuses unknown kinds and fields, text over 1 MiB, URLs over 2048 characters, a file name that is not one path segment, and labels with control or bidirectional override characters. `matchOsRequest` accepts only URLs with this application's scheme (or its `web+` form) and `https` links on a configured verified host for a handler that declares `verified`; it refuses credentials, fragments, dot segments and encoded slashes, and validates parameters and extras with the handler's own schema. A template can name only the request's own fields, so a sender cannot pick a different resource kind, screen or command. A prefilled value must fit its input property's type, `maxLength` and `enum`; the command validates the whole input again when a person submits.

`buildInstruction` takes the scheme, host, directory root, intent action and package from the declaration. Open-action values are encoded with `encodeURIComponent`, so a value stays inside its path segment, and the parsed result must keep the template's scheme and host. File paths are relative, without empty, `.` or `..` segments, and are joined below a configured root; the adapter still resolves links before it opens anything. A `notify` action is refused here because the plugin that issues its reply nonces builds it.

The mobile adapter takes a URI the OS opened the app with: a link in the application's scheme or `https`, or a `content:` or `file:` file, at most 2048 characters; anything else is dropped before it is matched. A file is inspected first and read only when a declared file handler lists its extension or its reported media type, within that handler's `maxBytes`. On Android a `content:` name is often an opaque id, so such a file matches by the media type its provider reports, and that type is the one a blob is stored as. A URI the bindings report as a share (on Expo, `<scheme>://expo-sharing`) is not matched as a link: its items are submitted as share requests, at most `maxSharedItems`, and a shared file is read only when a share handler accepts its media type, within that handler's `maxBytes`. A relayed open is checked against the declarations again, a share shows the system share sheet only when the bindings supply one, and reveal and open-file are refused on mobile. A notification is shown only when the bindings supply `notify`. Its buttons, nonces included, go into the notification's data, because a reply may come after the app was stopped. `replied` therefore treats the buttons it gets back as unknown input and submits a reply only for a button among them. `intent` takes an activity intent the device received, as unknown input, and submits it only when its action is a declared intent handler's; the device is asked to pass on only those actions and the extras their handlers declare (`intentListening`). An intent action starts only when the bindings supply `startIntent`, and only after its action id, intent action and package are checked against the declaration again and its extras are flat values. Intent handlers are registered through the framework's `@agent-native/mobile/intent-filters` config plugin, not Expo's `android.intentFilters`, which would prefix the declared names.

The generators produce verified link registrations only for hosts the deployment configures, never from content. Share handlers produce one share target per platform that accepts what they accept together; which handler a share reaches is still decided by the matcher. `associationFiles` lists only handlers that declare `verified`, with their parameters as wildcards, and refuses a team id that is not ten upper-case letters or digits, a certificate fingerprint that is not 32 colon-separated hex bytes, and an application with no verified link. Serving the files on the domain is the deployment's job.

The desktop adapter reads a command line only after `--` when one is present, so a link that breaks out of its quotes cannot add an argument that is read; without `--` it ignores every switch. It accepts links in the application's scheme and absolute local paths, and refuses UNC paths, which would make Windows authenticate to a remote server. Data a second instance hands over is parsed again. It reads only files a declared file handler lists by extension, within that handler's `maxBytes`, so other files the OS passes are never read. `fileRequest` sends a text payload inline only when it is strict UTF-8, and uploads a blob payload as the reported media type only when the handler declares it, otherwise as the one the handler declares for the extension. The upload is staged under the shell's own session: the blob store lets only that principal attach it, only within the grace period and only through a command whose blob limits accept it, and sweeps it when nothing does. The matcher refuses a blob whose media type the handler does not declare or that differs from the type the request reports, so a file cannot match as one type and be stored as another. A relayed open is checked against the declarations again before it runs. `openActionFor` matches a URL a page asked to open to a declared open action: same origin and path shape, no credentials, fragment or repeated parameter, and every value within the JSON form of the action's schema (text with `const`, `enum`, `pattern` and `maxLength`). It needs only that JSON form, so it works on declarations read over HTTP; a value it cannot check fails. `landingRequest` accepts a browser landing only with exactly one `os` (a link of at most 2048 characters) or `os-shortcut` parameter, or an `os-share` claim code of 22 to 64 base64url characters. A claim names input a plugin holds; the shell port resolves it through that plugin before matching. A launcher entry opens `<scheme>:///?os-shortcut=<id>`: no host, an empty path and only that parameter. `matchOsRequest` reads such a link as its shortcut before it matches links, so a link handler on `/` never receives it, and an undeclared id matches nothing. The desktop adapter hands the declarations to `launchers` once it has read them, and a launcher that fails to register is reported, not fatal. The desktop adapter runs a share action only when its caller supplies a share menu, which the Electron shell does on macOS. It runs a notify action only when its caller supplies `notify`. The buttons stay in memory, and a chosen one submits its reply; the authority checks the nonce, not the adapter.

## Dependencies

Framework: `@agent-native/contracts`. No external packages.

## Tests

```sh
bun test packages/shell
```

`test/desktop.test.ts` covers command lines with and without `--`, injected switches, relative and UNC paths, second-instance data, URLs that differ from a declared open action, input buffered until connect, undeclared files left unread, a blob file uploaded before it is submitted and an oversized one never read whole, relayed actions checked again, page opens with and without the shell port, and a relayed notification whose chosen button submits its reply while an unknown button submits nothing. `test/files.test.ts` covers handler lookup by extension and media type, text and blob request building, the upload media type, size limits and refused uploads, and the matcher's blob size and media type checks. `test/shell.test.ts` covers scheme, `web+` and verified links; links that are not the application's own or are malformed; a text file that prepares a form, size and field limits, and unsafe file names; open URLs that keep their host whatever the parameters hold; file paths kept below their root; and native, desktop and web registrations from one set of handlers. `test/associations.test.ts` covers the association files and their refusals. `test/shares.test.ts` covers the web manifest's share target and the `expo-sharing` config plugin from the share handlers, the share handler lookup and file request limits, claim codes and their landing, and a mobile shell without share bindings. `test/shortcuts.test.ts` covers the shortcut link form and the links that are not one, the shell port reading a shortcut link before a root link handler, the native, web and desktop launcher entries from one set of handlers, and a failing launcher registration leaving the desktop shell connected. `test/intents.test.ts` covers intent matching by action, categories, data scheme and MIME type with the extras schema, the listening map and received records, the intent instruction and its recheck before it starts, and the intent filter config plugin entry. The mobile adapter runs end to end in the OS plugin's `test/mobile.test.ts`, its notifications in the notifications plugin's and its intents in the Android intents plugin's.
